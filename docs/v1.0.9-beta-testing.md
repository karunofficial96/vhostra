# Vhostra 1.0.9 beta.1 physical testing

This is an internal, unpublished test build. The six native GitHub Actions jobs build ten installers and run automated package checks; they do not establish that login, shutdown, GUI launch, or Docker integration works on a physical machine. Record those results using the [cross-platform acceptance checklist](startup-acceptance.md) and, on macOS, the [Mac checklist](macos-startup-acceptance.md).

## Obtain and verify an installer

After an approved commit is pushed to `test/v1.0.9-startup`, open the repository's **Actions** tab, select **Package Vhostra 1.0.9 beta for testing**, and open the successful run for the exact commit being tested. Under **Artifacts**, download `verified-vhostra-beta-1.0.9`. Extract it; it contains all ten installers, `SHA256SUMS`, and `release-manifest.json`. The six `vhostra-<platform>-<arch>` artifacts are intermediate package outputs. Use the verified artifact only after the `verify` job succeeds. A failed or incomplete run is not a test candidate. The filename and packaged app version must contain `1.0.9-beta.1`.

| System | Choose this file (all start with `Vhostra-1.0.9-beta.1-`) |
| --- | --- |
| Apple Silicon Mac | `macos-arm64.dmg` |
| Intel Mac | `macos-x64.dmg` |
| Windows x64 | `windows-x64.exe` (NSIS) |
| Windows ARM64 | `windows-arm64.exe` (NSIS) |
| Debian/Ubuntu x64 or ARM64 | `linux-amd64.deb` or `linux-arm64.deb` |
| RPM distribution x64 or ARM64 | `linux-x86_64.rpm` or `linux-aarch64.rpm` |
| Linux AppImage x64 or ARM64 | `linux-x86_64.AppImage` or `linux-arm64.AppImage` |

Keep `SHA256SUMS` next to the extracted installer. On macOS run `shasum -a 256 Vhostra-1.0.9-beta.1-macos-arm64.dmg` (substitute your file); on Linux run `sha256sum -c SHA256SUMS` in the directory containing all ten files, or compare `sha256sum <filename>` with that file's entry if only one installer was retained. On Windows run `Get-FileHash .\Vhostra-1.0.9-beta.1-windows-x64.exe -Algorithm SHA256` in PowerShell and compare the 64-digit hash with the exact filename in `SHA256SUMS`. Stop if the values differ. `release-manifest.json` lists the same artifact names and hashes.

## Protect an existing installation first

This beta keeps the existing `com.vhostra.app` identity, product name, profile path, CLI integration, and Docker Compose project identities. Installing it to the usual location **replaces the v1.0.8 application** and uses the same data. It is not an isolated side-by-side test. Do not run stable and beta concurrently against one profile or Docker environment. If you need to keep stable installed, use a separate test machine or an independently isolated OS account and Docker environment; a separate app identity has not been implemented or verified.

Before replacing a working v1.0.8 installation:

1. In **Settings**, note the **Local configuration path** and current startup and service settings. Record representative Site document roots, database names/tables, certificates, and the current CLI path. Keep a copy of the working v1.0.8 installer.
2. Use **Settings → Export Full Backup**. Keep the backup manifest together with its private sibling folder in a trusted location; it includes database data, users, grants, and private authentication metadata. Confirm both parts exist and copy them outside the active Vhostra data directory. An **Export Configuration** bundle alone omits databases, website files, secrets, and private keys.
3. Independently copy every external website document root and any other files outside Vhostra's managed root. Preserve permissions and verify representative files in the copy. Keep a separate copy of the Vhostra configuration root, including certificates and backups, after services are stopped; do not treat a live MariaDB datadir copy as a database backup. Keep any separately managed Docker volume backup if your setup uses one.
4. Quit Vhostra, ensure Vhostra services have stopped before making a cold filesystem copy, and keep the backups untouched during testing. Do not use **Reset Vhostra**, remove Docker volumes, or import a backup merely to install this beta.

The installer and ordinary startup are intended to reuse existing settings, Sites, external document roots, MariaDB data, certificates, backups, Docker projects, and CLI configuration. The full backup is a recovery precaution, not a substitute for checking those items after installation. On macOS, replace only `Vhostra.app` in Applications; keep the data directory and any `/usr/local/bin/vhostra` link. Windows NSIS and Linux DEB/RPM install into the existing application identity and package location. See the [v1.0.8 installation guide](install.md) for platform-specific installer behavior and security prompts.

## Run the acceptance pass

Use the linked acceptance checklists for detailed steps and result recording. On each target, test **Manual** and **Run Services When Vhostra Opens** with **Launch Vhostra on Login** both unchecked and checked. Test **Run Services on Login** with the checkbox automatically unchecked and disabled. Switch away and confirm it is enabled but remains unchecked. Restart the app and then the OS for each state; confirm settings persist. Check that disabled Redis and Memcached remain disabled.

Repeat service-on-login cases while Docker starts late and while it is unavailable. Check the bounded retry, error reporting, manual recovery, already-running services, and a partially running environment. Test manual Quit and window Close separately from OS logout/sign-out, restart, and shutdown, both with a window and in background-only mode. After each cycle compare existing Site files, database tables, Docker volumes, certificates, backups, and settings with your baseline. Run `vhostra --help` and a read-only CLI status command from a fresh terminal; verify the CLI still points to the intended installation and profile. For AppImage, keep its executable at a stable path before enabling XDG autostart.

If a test fails, use the app's **Logs** page and inspect `application.log` under the active configuration path's `logs` directory; startup failures are recorded there. Include the OS version, architecture, installer format, desktop environment where relevant, Docker version, exact beta filename, Actions run and commit, preference combination, steps to reproduce, expected and actual behavior, and redacted log excerpts in a bug report. Never attach database dumps, private keys, passwords, or unredacted profile files.

Known limits: the macOS beta is ad hoc signed and not notarized; its login item may fail on a real Mac. macOS and Linux logout do not have a portable confirmed-termination signal. Windows session-end behavior needs physical verification, particularly in background-only mode. Linux XDG autostart depends on the desktop session. The CI Windows install/uninstall and Linux DEB checks run on hosted runners; RPM installation on an RPM distribution, AppImage desktop integration, and all physical OS login/shutdown behavior still require manual testing.
